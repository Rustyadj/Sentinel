Audited at HEAD `c315139` ("Add Gemini CLI as a first-class Sentinel runtime and Agent"), read-only. `d86d66b` (tip of `feature/agent-model-control-and-learning-finish`, pre-Gemini) was used as a reference point via `git show d86d66b:<path>` and `git show d86d66b --stat`; it changed only `src/app/chat/page.tsx` (69 lines) relative to `c315139`'s parent, so this audit treats HEAD as "current shipped state" without checking anything out. The Gemini commit (`c315139`) is otherwise out of scope; it touched `src/lib/agents/model-policy.ts`, `src/lib/agents/runtime/{cli-adapter.ts,config.ts,gemini.ts,service.ts,status.ts,types.ts}`, `GEMINI.md`, a migration, and one test — noted only where it changed a file this audit also cites for another worker.

**Headline finding: this codebase is far more built-out than a typical "audit before building" scenario implies.** A real Task/dependency/worker-router/execution-lock/worktree/approval/Guardian orchestration loop (`src/lib/orchestration/lisa-loop.ts`) already exists and already drives Claude Code and Codex as real subprocess workers under Hermes Lisa's direction. This is not a green-field build — it is close to the "Minimum Viable Build Mission" already, with specific named gaps (see §3, §5).

## 2. Cross-Cutting Systems — What Exists

- **Task/Job/Workflow model** — `prisma/schema.prisma:530-` `Task` model. **Dual-purpose by design**: a plain kanban task (`status`, `priority`, `assignee`) *and* a `CollaborationTask` node in a room's DAG when `chatRoomId` is set, with `dependsOnTaskIds` (real dependency graph, string array), `capabilities`, `fileScope`, `branch`/`worktreePath`. **This already is the "Build Mission" task graph** — extend it, do not build a parallel one. Orchestration logic lives in `src/lib/orchestration/lisa-loop.ts` (530 lines): `createTask`/`assignTask`/`startTask`/`createDependency`/`requestReview`/`mergeTask` tool handlers (`lisa-loop.ts:175-379`), worker selection via `src/lib/orchestration/worker-router.ts` (`selectWorker()`), and a real acceptance gate `validateCompletion()` (`lisa-loop.ts:391-407`) that independently checks unfinished tasks, pending approvals, unresolved disagreements, and open locks before Lisa's `DONE` claim is honored — Lisa's self-reported completion is not trusted.
- **Event system** — `AgentRuntimeEvent` (per-session runtime events, sequence-numbered via Postgres advisory lock at `store.ts:102`) and a separate `CollaborationEvent` stream (`emitCollaborationEvent`, `src/lib/orchestration/event-bus.ts`) for room-level orchestration events (`task.created`, `task.claimed`, `approval.requested`, `decision.created`, etc., used throughout `lisa-loop.ts`). SSE fanout for runtime events: `agent-sessions/[sessionId]/events/route.ts` (polling-based, 500ms interval, not push-based pub/sub — see §3 gaps). A third, learning-specific event stream exists: `src/lib/learning/event-service.ts` / `src/app/api/neural/stream/route.ts`.
- **Approval system** — two layers: `src/lib/orchestration/approval-gate.ts` (regex-based `assessRisk()` — HIGH_RISK_PATTERNS match `prisma migrate deploy|reset`, `drop table`, `rm -rf`, `force-push`, etc.; MEDIUM_RISK_PATTERNS match `migration`, `deploy`, `secret`, `credential`, `auth config`) creates `ApprovalRequest` rows scoped to a resolved `workspaceId`; `lisa-loop.ts:95-108` (`ensureApprovalCleared`) blocks `startTask` until a pending approval is resolved. A second, independent layer is Guardian (below) — the two are documented as deliberately not the same gate (`guardian.ts:3-6`: "Guardian does not replace the canonical risk gate — it observes/reviews/blocks around it").
- **Audit log** — `src/lib/workspaces/audit.ts` (`writeAuditLog()`), called from `chat-routing.ts` (session start/task sent) and `delegation.ts` (session delegation) with `workspaceId`/`projectId`/`userId`/`action`/`entityType`/`entityId`/`details`. Real, not stubbed.
- **Learning Core** — `src/lib/learning/` (30+ files: `experiment-orchestrator.ts`, `guardian.ts`, `production-failures.ts`, `redaction.ts`, `sandbox.ts`, `adversarial.ts`, etc.). Evidence flow: `store.ts:117-129` — every `agentRuntimeEvent.append()` call inspects the event for a failed tool call, failed command, or generic error and calls `recordProductionFailure()` (`src/lib/learning/production-failures.ts`) with `sourceId`/`workspaceId`/`userId`/`context`. Chat turns feed `Experience` rows via `captureAgentTurn()` (`src/lib/neural-engine/chat-capture.ts`), which runs `autoEvaluateExperience()` — a real Observe→Act→Measure→Evaluate→Propose pipeline, not a stub (per the file's own doc comment, `chat-capture.ts:1-16`). **`Experience.cost` is a nullable `Float?` field (`prisma/schema.prisma:940`) that is never populated on the chat/runtime execution path** — `chat-capture.ts`'s `startExperience()` call does not set `cost` (grepped, not present in the params passed). See §3 (real cost accounting gap) — importantly, the existing UI (`AgentOperations.tsx:30`, `mission-control/server.ts:159-168,223`) already reports `costToday: null` / "Cost unavailable" rather than `$0.00` when no data exists, so **the "no fake UI" principle is already respected for cost**, it's just that no real cost is ever computed to report.
- **Guardian** — `src/lib/learning/guardian.ts`, real server-side enforcement, not advisory-only. `evaluateGuardian()` classifies risk via `classifyRiskLevel()` (`src/lib/neural-engine/policy-service.ts`, not read in full) into tier 1/2/3 → mode observe/review/block; deterministic `HARD_BLOCK_PATTERNS` (`guardian.ts:42-62`) catch prompt-hierarchy-override, credential-exfiltration, path-traversal (`(\.\.\/){2,}|\/etc\/(passwd|shadow)`), and fake-approval-marker attempts and block immediately with no human round-trip; tier 3 always requires `humanAuthorized` (`guardian.ts:124-133`) — no trust score or Guardian confidence can substitute; Guardian is explicitly forbidden from approving its own elevation (`isSelfElevation` check, `guardian.ts:113-118`, and `resolveGuardianReview()` rejects a reviewer resolving their own decision, `guardian.ts:214-216`). **However**: I did not find `evaluateGuardian()` called anywhere in the CLI/Hermes runtime adapters or `lisa-loop.ts` — it appears wired into the Learning Core's own candidate-promotion/skill-generation pipeline (`graph-sync.ts`, `candidate-executor.ts`) but **not into the agent-execution path itself** (worker `startTask`/`send`). Flagged in §4.

## 4. Gaps

1. **No durable background execution for missions.** Lisa's loop and the CLI adapters run synchronously within one server request's lifetime (bounded by `MAX_LISA_ITERATIONS = 25` and a 10-minute per-task-turn timeout). There is no BullMQ job wrapping a full mission, so a mission that should run for hours/across a Sentinel restart has no persistence/resume mechanism today beyond individual `AgentSession` rows and the `stale_session_lock` health signal (which detects staleness but doesn't drive automated recovery).
2. **Guardian is not wired into the runtime execution path.** `evaluateGuardian()` exists and is genuinely strict (hard-blocks, tiered human approval, self-elevation refusal) but is only invoked from the Learning Core's candidate/skill pipeline, not from `lisa-loop.ts`'s `startTask`/`runImplementation` or the CLI adapters' `send()`. Autonomous coding-worker actions today are risk-gated only by `approval-gate.ts`'s simpler regex `assessRisk()`.
3. **Real cost/token accounting does not exist**, despite the aggregation and "unavailable, not $0.00" UI scaffolding being in place (`mission-control/server.ts`, `AgentOperations.tsx`). No adapter currently parses token usage from Claude Code's/Codex's/Hermes's stream output into `Experience.cost`.
4. **Two out-of-sync sources of truth for Nathan2's endpoint** (`registry.ts:64` says `4861`; `runtime/config.ts:54` says `4864`, with a code comment noting 4861 "answered nothing"). Left over from a partial migration off `registry.ts` onto the DB-backed `AgentRuntime`/`config.ts` system — likely applies to other fields too since `registry.ts` still exists in parallel with `runtime/config.ts`'s `COMPATIBILITY_RUNTIMES`.
5. **SSE runtime-event fanout is polling-based (500ms), not push/pub-sub**, and self-terminates after a fixed 30s connection deadline (`events/route.ts:21`) — the client must reconnect. Fine for the current single-turn UI; may need a real pub/sub layer (Redis, which is already present for BullMQ) if the UI needs snappier multi-worker live views.
6. **No single canonical "Mission" entity distinct from a chat room's task set** — a mission today is implicitly "the tasks in `chatRoomId` X". Naming/UX-level gap more than an architecture gap, since the Task model already carries everything needed.
7. **Neural graph "active path" highlighting**: not confirmed present (see §2, marked UNKNOWN) — needs verification before assuming it's reusable as-is for visualizing an in-flight mission.
8. **Claude Code / Codex worker file-claim system (`ExecutionLock`) uses coarse glob-prefix overlap detection** (`patternsOverlap()`, `execution-lock.ts:9-13` — string-prefix match on the pattern with wildcards stripped), not real per-file locking; two tasks with only *coincidentally* overlapping prefixes (e.g. `src/lib/a*` vs `src/lib/ab*`) would conflict even without a real file overlap, and conversely a lock on `src/**` vs `src/lib/**` would correctly conflict but finer-grained cases may not be handled precisely. Worth a closer look before scaling to many concurrent workers.
9. **`sensitive-config.ts` only guards the runtime-configuration UI**, not the general chat/event/Learning-Core paths — see Security Risks below, this is really a risk not just a gap.

## 5. Security Risks

Concrete, code-referenced, ranked roughly by severity for "give coding agents more autonomous multi-worker access":

1. **Guardian is bypassable for the exact actions that matter most (autonomous code execution).** `evaluateGuardian()`'s hard-block patterns (prompt-hierarchy-override, credential-exfiltration, path-traversal, fake-approval-marker — `guardian.ts:42-62`) never see a prompt that goes through `lisa-loop.ts` → `runAgentTurn()` → the CLI adapters. Only `approval-gate.ts`'s much simpler `assessRisk()` regex list runs on that path. **This is the single biggest security gap found** — a prompt-injected coding worker whose *action text* would trip Guardian's `path_traversal_attempt` or `credential_exfiltration_attempt` pattern is not evaluated by Guardian at all today; it only hits `approval-gate.ts`'s `MEDIUM_RISK_PATTERNS`/`HIGH_RISK_PATTERNS`, which do not include those categories.
2. **Secret exposure to chat/events/Learning Core is not comprehensively blocked.** `containsSensitiveRuntimeConfig()` (`sensitive-config.ts`) is documented as guarding only "the runtime configuration UI" — it is not invoked from `store.ts`'s `append()` (which persists every raw stdout/stderr line and tool-call payload from Claude Code/Codex into `AgentRuntimeEvent.payload`, then feeds failures into `recordProductionFailure` → Learning Core), nor from `chat-routing.ts`'s `persistChatExchange`/`appendSessionMemory`. If a coding worker's stdout or a file it reads contains a real credential (e.g., cats a `.env`), nothing found in this audit prevents that text from being persisted verbatim into `AgentRuntimeEvent`, the chat transcript, and session memory — all readable later by whoever has session/room access, and potentially propagated into Learning Core evidence. `src/lib/learning/redaction.ts` exists and may address the Learning-Core leg specifically — **UNKNOWN**, not read in this pass; needs direct verification of what it actually redacts and where it's called from before relying on it.
3. **Codex's `--skip-git-repo-check` flag removes one of Codex's own built-in safety heuristics** (`codex.ts:21-25`) on the stated reasoning that Sentinel's own sandboxing supersedes it — reasonable given `path-security.ts` and worktree isolation, but it does mean Codex's own "am I in a directory I should be touching" check is fully delegated to Sentinel with no defense-in-depth from Codex's side; any bug in `resolveAllowedWorkingDirectory`/`ensureTaskWorktree` has one fewer independent backstop for Codex specifically (Claude Code has no equivalent bypassed check).
4. **Prompt injection into coding workers is not filtered before it reaches the CLI.** `CliRuntimeAdapter.send()` validates the prompt is non-empty, has no null bytes, and is under 100,000 characters (`cli-adapter.ts:180-182`) — this is a well-formedness check, not a content/injection check. Task descriptions, file contents the worker reads, or a compromised peer worker's `RESULT` message feeding into `buildAgentContext()` for the next task could carry adversarial instructions with no scanning layer before they reach Claude Code/Codex's actual prompt. Guardian's hard-block patterns would catch the crudest cases (`ignore ... instructions`) *if* Guardian were wired in (see risk #1) — currently nothing catches even that.
5. **Forged task/workspace ownership**: appears reasonably well-defended — `delegateSession()` fails closed on workspace mismatch and requires `source.userId === input.actorUserId` (`delegation.ts:46-48`), `requireSessionAccess` enforces session ownership. Not flagged as a top risk, but **not exhaustively verified** — did not trace every API route under `src/app/api/agent-sessions/` and `src/app/api/tasks/` for consistent enforcement; recommend a follow-up pass specifically walking each route handler.
6. **Main-branch push authority**: `mergeTaskBranch()` (`worktree-manager.ts:70-79`) runs a real `git merge --no-ff` directly into whatever is currently checked out at the runtime's root — there is no separate human-approval gate specifically for *merging* (as distinct from the approval gate for *running* a risky task). A worker could complete a low-risk-classified task (no approval required) whose diff is nonetheless landed directly into the shared root via `mergeTask`, with only Lisa's own judgment (not a deterministic gate) deciding whether the risk classification was accurate at merge time. Given `assessRisk()` is a static regex over `task.title`/`description`/`fileScope` — not the actual diff content — a task whose *description* looks benign but whose *actual patch* touches something sensitive would sail through both the approval gate and the merge with no additional check on the diff itself.
7. **`safeRuntimeEnvironment()` allowlist is reused for both the *runtime binary invocation* and the *worktree git commands*** — worth confirming (not verified) that `git` itself doesn't need additional env vars (e.g. `GIT_SSH_COMMAND`, credential helpers) that aren't on the allowlist, which could cause silent auth failures rather than a security hole, but is adjacent enough to flag.

## 6. Minimum Viable Build Mission

**User → Sentinel chat → Lisa → delegates to Claude Code + Codex (real runtimes) → Lisa reconciles → user sees real result** — smallest change set, reusing what exists:

1. Chat message arrives at Lisa's runtime via the existing `chat-routing.ts` (`RUNTIME_AGENT_MAP["hermes-lisa"]`) — **already works**.
2. Lisa's response is parsed for tool directives and, if the objective needs implementation work, the existing `runLisaLoop()` is invoked with `pool: ["claude-code", "codex"]` — **already works mechanically**; what's missing is the trigger wiring from an ordinary chat turn into `runLisaLoop()` (currently `runLisaLoop` appears to be called from room/task orchestration entry points, not verified as directly reachable from a plain `/chat` message — **UNKNOWN**, needs a trace of what calls `runLisaLoop()` today, e.g. `grep -r runLisaLoop src/app/api`).
3. Lisa's `createTask`/`assignTask`/`startTask` tool calls create real `Task` rows and dispatch to Claude Code/Codex through `runAgentTurn()` → the real CLI adapters, each in its own git worktree (`ensureTaskWorktree`) — **already works**.
4. Real-time visibility: SSE per `AgentSession` — **already works**, needs a UI surface tying a mission's `chatRoomId` to its constituent sessions' event streams (may already exist in `CollaborationRoom`, not fully audited).
5. Reconciliation: `requestReview` (cross-worker review) and `mergeTask` (real `git merge`) — **already works**, gated by `validateCompletion()` before Lisa can claim `DONE` — **already works**.
6. **The two things to actually build**: (a) wire `evaluateGuardian()` into `runImplementation()`/`startTask` before a coding worker executes (closes risk #1), and (b) confirm/build the trigger path from ordinary chat into `runLisaLoop()` if it doesn't already exist for non-room-scoped chat.

Everything else needed for the MVP already exists in code, not just in spec.

## 7. Phase Plan

### Phase A: Runtime + Mission truth (detailed)

**Goal**: close the two concrete gaps above and remove the one live correctness bug found, without inventing new systems.

Expected files to change:
- `src/lib/agents/registry.ts:64` — fix `HERMES_NATHAN2_ENDPOINT` default from `4861` to `4864` to match `runtime/config.ts:54` (or better: delete `registry.ts`'s static endpoint fields entirely and make it read from `runtime/config.ts`'s `COMPATIBILITY_RUNTIMES`/DB rows, eliminating the dual-source-of-truth risk for good).
- `src/lib/orchestration/lisa-loop.ts` (`runImplementation`, around line 114-173) — call `evaluateGuardian()` before `runAgentTurn()` for coding-runtime tasks, blocking on `verdict === "block"` and surfacing `verdict === "hold"` as a new task status/approval path (reusing `ApprovalRequest` for the human resolution UI or building on `resolveGuardianReview()`).
- `src/lib/agents/runtime/store.ts` (`append()`, around line 100-131) or a new `src/lib/agents/runtime/secret-scan.ts` — apply a `containsSensitiveRuntimeConfig()`-equivalent check (probably needs to be less strict/more targeted than the config-UI version to avoid false-positiving on legitimate code diffs) before persisting event payloads, or redact matches before they reach `AgentRuntimeEvent`/chat/Learning Core. Needs a decision on redact-vs-block.
- `src/lib/learning/redaction.ts` — read fully and confirm/extend its coverage to the runtime event path if it doesn't already cover it (currently UNKNOWN whether it's wired there).
- Trace and, if missing, wire the `/api/chat` → `runLisaLoop()` trigger path (`grep -r runLisaLoop src/app/api` first to confirm current wiring).
- Add real token/cost parsing to at least one adapter (`claude-code.ts` and `codex.ts` JSON stream output both carry token counts in their native formats — Claude Code's `result` event and Codex's `turn_context`/final frame) feeding into `Experience.cost` via `chat-capture.ts`/`captureAgentTurn`.

Acceptance criteria:
- A coding-worker task whose action text matches a Guardian `HARD_BLOCK_PATTERN` is blocked before the subprocess spawns, with a `GuardianDecision` row created and visible in the mission's event stream.
- `registry.ts` and `runtime/config.ts` report the same Nathan2 endpoint (single source, ideally).
- A synthetic secret-shaped string appearing in a worker's stdout does not appear verbatim in the persisted `AgentRuntimeEvent`, chat transcript, or any Learning Core experience/event record (test with a fixture that inserts a `sk-...`-shaped string into mocked CLI output).
- `Experience.cost` is non-null after at least one real Claude Code or Codex turn, computed from actual reported token counts, not estimated/hardcoded.
- A chat message sent outside any pre-existing room/task context can still trigger a real multi-worker mission via Lisa (or the audit confirms and documents that this already works, with the call path cited).

### Phase B: Lisa orchestration (summary)
Extend `lisa-loop.ts`'s existing tool-calling loop rather than replacing it: richer worker-selection signals from `getRoutingHistory`/`adaptive-routing.ts`, smarter parallel-task batching (already partially present via `startDirectives` running concurrently), and better failure-recovery prompts when a `ModelUnavailableError` or Guardian block interrupts a task mid-mission.

### Phase C: Isolation (worktrees, file claims) (summary)
Harden `execution-lock.ts`'s glob-prefix conflict detection into real path-set overlap (not string-prefix matching), and consider per-file (not per-task) locking granularity for high-concurrency missions; worktree cleanup (`removeTaskWorktree` exists but its call sites weren't traced — confirm worktrees are actually reaped after merge/cancel, not just created).

### Phase D: Integration + verification (summary)
Wire `mergeTask`'s diff (not just the task's stated `fileScope`/description) through `assessRisk()`/Guardian before merge, closing risk #6; add automated reconciliation for `stale_session_lock` (currently detected but not auto-recovered) so a Sentinel restart mid-mission resumes or cleanly fails tasks rather than leaving them stuck.

### Phase E: UI (summary)
Surface mission-level views on top of existing per-session SSE streams and the `CollaborationRoom`/mission-control components already in place; confirm and, if absent, add "active path" highlighting on the neural graph tied to a live mission's task DAG.

### Phase F: Learning (summary)
Extend the already-real Learning Core (`production-failures.ts`, `evaluator.ts`, Guardian evidence) to specifically learn from multi-worker mission outcomes — e.g., feeding `worker-router.ts`'s selection heuristics from `getAgentRoutingStats` more richly, and closing the loop on real cost data (once Phase A adds it) as a factor in worker/model selection.
